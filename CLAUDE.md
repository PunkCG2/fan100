# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Single PowerShell 7 script, `Fans30.ps1`, that forces all motherboard/GPU/CPU fan controls to 100% for a fixed time (or until a key is pressed), then restores firmware control. Hardware access comes from `LibreHardwareMonitorLib.dll` (must sit next to the script; loaded via `$PSScriptRoot`). No build, lint, or test setup.

## Running

```powershell
pwsh -File Fans30.ps1                # 60 s (default)
pwsh -File Fans30.ps1 --time 180     # N seconds
pwsh -File Fans30.ps1 --endless      # until keypress; ignores --time
Fans.cmd --time 180                  # same flags; installs PowerShell 7.6 first if missing
```

Requires Windows and `pwsh` (not Windows PowerShell). Prebuilt `.lnk` shortcuts (`Fans 1min`, `Fans 3min`, `Fans Endless`) call the script with an absolute path; recreate them if the folder moves. In timed mode `Esc` aborts the countdown early; in endless mode any key ends it.

## Architecture notes

- **Launcher `Fans.cmd`**: covers the one dependency the script cannot install itself, PowerShell 7.6+ (the DLL targets .NET 10, so the check is `[Environment]::Version.Major -ge 10`, not the PS version). It looks for `pwsh` on PATH, then in `%ProgramFiles%\PowerShell\7`, installs or upgrades `Microsoft.PowerShell` with winget if needed, and runs the script with the full path, because the console does not see the new PATH. It must stay ASCII with CRLF line endings (`.gitattributes` enforces CRLF): with LF, cmd misparses the file. Never put parentheses in a `rem` inside a `( )` block. `Fans30.ps1` repeats the .NET check at the top, before elevation, for people who run it directly.
- **Self-elevation**: if not admin, the script relaunches itself with `Start-Process -Verb RunAs`, forwarding `$args` via `-join ' '`. Arguments containing spaces would break; current flags don't. It uses `pwsh` by name when it is on PATH (the Store build lives under `WindowsApps`, and launching that path directly with RunAs is unreliable), otherwise `[Environment]::ProcessPath`, which is the case right after `Fans.cmd` installs it.
- **Single instance**: after elevation it takes the named mutex `Local\Fan100.Enfriamiento`. Two traps here, both already paid for once:
  - `Mutex.WaitOne` returns `$true` when *this* process acquired it, so `$yaHayInstancia = -not $mutex.WaitOne(0, $false)`. Inverting it made the script always report "another run is in progress" and never start. Mutexes are also re-entrant per thread, so a test in the same process re-acquires its own mutex and sees a false negative; each check needs its own process.
  - `AbandonedMutexException` is the *good* path: the previous holder was killed, the exception still grants ownership, so keep going.
  - `Libera-Cerrojo` must release the mutex by hand. Relying on process exit is not enough: the non-elevated launcher process outlives its own `exit` long enough to block the relaunched script, and the close countdown would block a new run for 10 extra seconds. It is called in `finally`, after the fans are restored, and skipped when `$yaHayInstancia` is set (the mutex belongs to someone else). `Get-ProcBloqueante` names the holder so the user can act on it; `--forzar` is the escape hatch.
- **Library download**: if `LibreHardwareMonitorLib.dll` is missing, `Asegura-Libreria` downloads the pinned NuGet package (`$versionLib`), extracts only `runtimes/win-<arch>/lib/net10.0/LibreHardwareMonitorLib.dll` and checks it against `$hashesLib` before moving it next to the script. The x64 hash is the same file that is committed. To upgrade, change the version and both hashes together. A hash mismatch is a hard failure, never a warning. The DLL targets .NET 10, so `pwsh` must run on .NET 10.
- **PawnIO driver**: `LibreHardwareMonitorLib` 0.9.5+ reaches the hardware through the PawnIO driver. Without it nothing throws: CPU temperature reads 0, voltages read garbage (1.55 V everywhere) and no `Control` sensors appear, so the only symptom was "sin ventiladores". `Asegura-PawnIO` runs after the DLL check, checks for the `PawnIO` service and, if missing, installs `namazso.PawnIO` with winget (already elevated). It never aborts the run; `$hayPawnIO` only changes the "no fans" explanation. Pipe winget to `Out-Host` inside the function or its output becomes part of the return value.
- **Laptops**: the fan chip is usually an embedded controller (e.g. ITE IT8987, reported by LHM as an "Unknown ITE/Winbond/SMSC with ID 0x8987" LPC chip), which LHM cannot control. "No fans" there is expected, not a bug.
- **Input helpers**: `$conTeclado` (keyboard available, computed once after elevation) and `$consolaInteractiva` (real console, so cursor movement works) are separate flags with different fallbacks. Both are computed with a probe in a `try/catch`, never assumed.
- **Fan restore safety**: `FanGuard` is a C# class compiled with `Add-Type`. It holds the list of `IControl` objects and registers a `SetConsoleCtrlHandler` that calls `SetDefault()` on window close, logoff, or shutdown. It must be C# because the handler runs on another thread, where PowerShell script blocks can't run. Any control set with `SetSoftware(100)` must be added to `FanGuard.Controls` first. The `finally` block also calls `FanGuard.Restore()` for normal exit and Ctrl+C.
- **Restore verification**: `Restore(bool verificar)` returns one message per control that did not go back to firmware instead of swallowing exceptions. `$verificar = $false` from the ctrl handler (no time for it). Only `ControlMode.Software` counts as a failure: that is the mode the script itself set, so `Default`/`Undefined` never produce false alarms. `Describe()` prefers `Sensor.Hardware.Name + Sensor.Name` over `Identifier`, which is an `Identifier` object, not a string.
- **Sensor reporting**: `Read-Sensors` snapshots Temperature/Fan sensors before and after, keyed by `Sensor.Identifier`. Each entry carries `Hardware`, `Sensor` (name only), `Name` (`"Hardware / Sensor"`, used by the report) and `Value`.
- **Live panel**: the cooling loop shows a block redrawn in place once per second. Pipeline: `Get-PlantillaVivo` freezes the layout (hardware header, then that hardware's temperatures, then its fans); `Get-ColumnasVivo` decides 1-3 columns from the window width (40 chars per column, max 3); `Reparte-Vivo` splits hardware groups across the shortest column so a device is never split in half; `Recorta-Vivo` trims to the window height and adds the "... y N sensores más" row; `Get-LineasVivo` + `Formatea-CeldaVivo` render the frame; `Write-Vivo` draws it. Colour = green when the value moves the right way (temperature down, RPM up), red the other way, cyan when unchanged. Machines with 10+ fans are the normal case, not an edge case: a 7-fan board plus a 3-fan GPU does not fit in one column of a normal window.
- **Trim after splitting, never before**: `Recorta-Vivo` takes a `Reparte-Vivo` result, not a template. Trimming first and splitting after made the block grow back over the limit.
- **Live panel traps**: `[Console]::GetCursorPosition()` returns a `ValueTuple` and `$pos.Left`/`$pos.Top` resolve to *nothing* in PowerShell, so use `$pos.Item1`/`$pos.Item2`. After a draw the cursor sits one row *below* the block, so `Write-Vivo` must move up `$lineas.Count` rows, not `Count - 1`, or the whole block creeps down one row per refresh. Every line is padded to `WindowWidth - 1` so nothing wraps and leaves a stale row; keep header, footer and sensor rows under that width.
- **Sizing the panel**: `Get-LineasVivo` adds 4 fixed lines (header, blank, blank, footer) on top of the template rows, so `$maxFilas` is `WindowHeight - cursorRow - 6` (4 fixed + 2 rows of margin). Forget the fixed lines and the block overflows, the console scrolls and every redraw lands on the wrong rows. `$maxFilas = 0` means "not even one sensor fits": `Recorta-Vivo` returns an empty template and the panel degrades to header + countdown, which always fits. Machines with many fans (a 7-fan board plus a 3-fan GPU) hit this path often, so it is a normal case, not an edge case.
- **Rows are not all sensors**: `Recorta-Vivo` appends a "... y N sensores más" row that has text but no `Id`/`Unidad`, so `Get-LineasVivo` must branch on `$fila.Titulo -or $fila.Fija` before touching `$fila.Id`, or `$fanFin[$null]` throws and kills the whole cooling cycle.
- **Never swallow cycle errors**: the main block is `try`/`catch`/`finally`. Without the `catch`, a failure mid-cooling ran the restore and the close countdown and looked like the cycle had simply finished instantly; the message only appeared after 10 s of countdown. The catch prints the message and the offending line number, and sets `$motivoCorte = 'error'`.
- `SetCursorPosition`, `WindowWidth` and `WindowHeight` throw when there is no real console, hence `$consolaInteractiva` (set from `IsOutputRedirected` and confirmed with a `GetCursorPosition` probe) and the `try/catch` fallbacks: without a real console the panel prints once and the countdown goes back to a single line.
- **Report and log**: `Get-LineasInforme` builds the report as objects `{Texto, Color}`; `Write-Informe` prints them with color and `Add-InformeLog` writes the same `Texto` to `logs/coolingLog_yyMMdd.txt` (one file per day, appended, `utf8BOM` so Notepad shows the accents). Report headings must not mention colours: that text also lands in the log file, which has none. Format numbers with an explicit specifier (`{0:F1}`, `{0:N1}`): bare `{0}` on a double drops trailing zeros and uses an invariant decimal point, which clashed with the Spanish formatting of the rest. The `logs` folder is gitignored.
- **Auto-close**: `Espera-Cierre` ends the run instead of blocking on `ReadKey`. It counts down and exits immediately on a keypress; polling `[Console]::KeyAvailable` every 100 ms. It falls back to a plain wait when console input is redirected, so it must not assume a keyboard exists. Both end-of-script paths call it: the missing-DLL error and the `finally` block.
- **Close delay**: two constants at the top of the script, `$segundosCierre` (10 s) and `$segundosCierreCorto` (3 s). The normal run gets the long one because there is a sensor report to read; `$motivoCorte` is non-empty when there is no report (an `Esc` abort, or no controllable fans at all), so the `finally` block picks the short one.
- **Cooling loop timing**: the loop is driven by a wall-clock deadline (`$plazo = [DateTime]::UtcNow.AddSeconds($totalSegundos)`), never by counting iterations. Counting 60 one-second iterations made the run take as long as the work per iteration: reading every sensor twice plus rendering and redrawing the panel added ~250 ms per pass, so `--time 60` finished in ~90 s. Each pass now recomputes `$quedan` and sleeps only what is left. `Espera-Tecla` also clamps its 50 ms poll to the remaining time, because `Start-Sleep -Milliseconds 50` actually takes ~64 ms here (the default timer granularity), which added ~3 s on its own. Report the duration as measured, but it should now match the requested time within a few tenths.
- **Abort path**: `Espera-Tecla` is the input poll used by the cooling loop. It reports `$true` for `[ConsoleKey]::Escape`, or for any key when called with `-Cualquiera` (endless mode); other keys are consumed silently. `$motivoCorte` (`''`, `'Esc'`, `'sin ventiladores'` or `'error'`) is the single flag that skips the report and shortens the close wait; the control counter runs the same check before any waiting starts.
- Script messages and comments are in Spanish; keep that convention.
